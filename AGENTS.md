# AGENTS.md

Trailframe — photo gallery app: Python/FastAPI backend + React/TS/Vite frontend, pip-installable as `trailframe` (wheels on GitHub releases; single server serving the built frontend).

## Quick Reference

| Task | Command |
|------|---------|
| Run backend | `python -m trailframe.main` |
| Build frontend | `cd frontend && npm run build` |
| Lint backend | `ruff check .` |
| Format backend | `ruff format .` |
| Lint frontend | `cd frontend && npm run lint` |
| Test frontend | `cd frontend && npm test` |
| Run tests | `python -m pytest` |
| Build package | `npm run build && python -m build` |
| Kill backend | `netstat -ano \| findstr :8000` then `taskkill -PID <pid> -F` |

## Layout

- `trailframe/` — FastAPI app
- `frontend/` — Vite + React app
- `pyproject.toml` — metadata, deps, ruff config, hatchling build, console script `trailframe = trailframe.main:main`
- `supervisor.py` — restarts `python -m trailframe.main`

## Backend (FastAPI, Python 3.12)

### Core

- **Run**: `python -m trailframe.main` from repo root
  - `main.py` serves `frontend/dist` from CWD if present, else packaged copy
  - Flags: `--config` (default `config.yaml`), `--folder` (sets `photos`/`processed`/`trash` and other `*_folder` subdirs), `--database`, `--port` (8000), `--failsafe` (transient: skip `FolderService` scan/watch for this run only, never saved to config), `--openapi FILE`

- **Artifacts** (CWD, all gitignored): `config.yaml`, `gallery.db`, `photos/`, `processed/`, `thumbnails/`, `trash/`, `maps/`, `activities/`, `models/`, `tiles/`

- **Style**: ruff from root `pyproject.toml`

- **pip**: `torch` installed to `C:\pylibs` via `.pth` (Win long-path limit); use `pip install --target C:/pylibs <pkg>` for deep dirs

- **Releases**: build frontend first, then `python -m build`; attach wheel to GitHub release (no PyPI)

### Architecture

- **Services** (`trailframe/services/`): class-based `Service` singletons wired in `main.py` lifespan
  - `service.py` (base), `core/` (Configuration, Database, Statistics, ThreadPool), `photos/` (Folder, Processing, Thumbnail, Photo), `rules/` (Rule), `activities/` (Activity, GarminConnect, Gpx), `map/` (Map, Location, Tile), plus `pipelines/`, `scanners/`
  - `Service`: non-virtual `configure/start/stop` → virtual `_configure/_start/_stop`, `_log` (`[Name]` prefixed on stderr via `log.py`), state tracking; `_name` overrides
  - `_requires`: each service declares its direct dependencies as names (resolved against `ServiceRegistry` at start); `start()` verifies them — on violation logs an `ERROR` and raises (`Service._require_started`)

- **Pipeline** base: eager thread-safe queue (sync `add`/`start`/`stop`, `get_queue_size`, `accepts`); `stop()` drains worker and flushes run stats; `take_pending()` returns leftover items; `PipelineEmpty` sentinel accepted everywhere and dropped

- **Start order**: `ThreadPoolService` → `ExpressionEngineService` → `DatabaseService` (creates tables) → `HardwareService` → `PhotoService` → `TagService` → `RuleService` → `PipelineService` → `FolderService` → `ProcessingService` → `ThumbnailService` → `MapService` → `GarminConnectService` → `GpxService` → `ActivityService` → `LocationService` → `TileService` → `StatisticsService` → `DuplicatesService` → `SimilarityService` (order must satisfy `_requires`: DB→TP, Hardware→DB, Photos→DB, Tag→DB, Rule→DB+Tag, Pipeline→DB, Folder→DB+Pipeline, Processing→TP+Folder+Pipeline, Thumbnail→Photos, Garmin→DB+TP, Gpx→DB, Activity→DB+TP+Garmin+Map, Location→DB+TP, Tile→TP, Statistics→DB, Duplicates→DB+TP, Similarity→DB)

- **Concurrency**: one shared pool (`ThreadPoolService`, size `general.thread_pool_size`, default 2); all heavy work (scanners, maps, Garmin, tiles, geo); each pipeline = 1 worker task (`Pipeline._worker_count = 1`) — bounds memory (one YOLO inference at a time); DB work stays on event loop

- **Hardware detection** (`core/hardware_service.py`): `HardwareService` runs before `PipelineService` at configure time so scanner flags are already settled. It reads the free (available) physical memory with stdlib only (`GlobalMemoryStatusEx`/`ullAvailPhys` on Windows, `MemAvailable` from `/proc/meminfo` on Linux, `vm_stat` on macOS) and, below `MIN_FREE_RAM_GB` (1 GB), sets `scanners.<Name>.enabled = false` for every heavy scanner and defaults `general.javascript_modules` to `false` (an explicit config value always wins). The outcome is recorded only in the generic `app_data` table (key `hardware_detection`): free memory, threshold, heavy scanner names, the ones auto-disabled, and the `javascript_default`. Detection only re-evaluates heavy scanners missing from that record, so scanners added by a later release are covered without overriding a user's earlier enable/disable choice. The result is internal and deliberately not exposed through the API; `Hardware & performance` (`trailframe/docs/hardware.md`, `GET /api/docs/hardware`) explains the behaviour in the Help menu.

- **Call hierarchy**: content/enrichment = `Pipeline → Scanner → Service`; API content = `API → Service`, never a Scanner (map/wireframe via `LocationService`/`MapService`)

### Photos & Pipelines

- **Photo files** (`models/photo.py`, `models/photo_file.py`): the chain is `photos/` → `CreationPipeline` (`Processing` scanner) → `processed/` → the remaining pipelines. One `Photo` row describes both: `path`/`filename`/`file_size` are the **original** archive file (relative to `photos/`, `path` unique); `alternatives` is a JSON list of processed files (`{target_size, path, filename, file_size, width, height, main}`, path relative to `processed/`); `processing` is a separate JSON list of provenance in a two-stage shape (`{step, summary, details, meta}` — a headline summary, a `details` map of human-readable label → formatted value rendered verbatim by the UI, and a hidden `meta` object for frontend features). Accessors return a `PhotoFile` value object: `photo.original`, `photo.main()` (the entry flagged `main`, else the original) and `photo.alternative(target)`. Alternatives carry pixels only; EXIF stays on the original and orientation is baked in. Rows without alternatives (legacy libraries, or photos queued before a target was configured) keep working because `main()` falls back to the original, and the `Processing` scanner encodes them on their next pass.

- **PhotoService** (`photos/photo_service.py`): resolves and deletes photo files. `resolve(photo, file=None)` uses the provider for originals (default `FolderService`, `SOURCE = "File"`, plus `RemoteProvider` `SOURCE = "Remote"` for in-memory photos) and `ProcessingService` for alternatives; it defaults to `photo.main()`. `delete(photo)` removes every alternative and moves the original to the trash. Extensible to network/NAS backends.

- **ProcessingService** (`photos/processing_service.py`): owns `general.processed_folder` and the preprocessing driver. It decodes the original, runs the processor chain (`services/processors/`, fixed order Exposure → White balance → Contrast → Local contrast → Vibrance → Tilt → Crop → Noise reduction → Rescale → Sharpening) and encodes each target size (longest edge, default `[1080]`) into the processed folder (WebP, `processing.main`/`format`/`quality`); it knows nothing about the individual steps. `preprocess(photo)` is called by the `Processing` scanner inside the CreationPipeline: it is a no-op for remote photos, when no target is configured, and when every enabled processor already left its step in `photo.processing`; otherwise it regenerates the alternatives from the photo's own target set, removes the superseded files and invalidates the main-target thumbnails. `needs_processing(photo)` derives that from the recorded steps, so a processor added by a later release, or enabled in the config later, re-runs over the library on the next pipeline pass. `_requires = ("ThreadPoolService", "FolderService", "PipelineService")`; `_reconfig_safe = False`.
  - `reprocess(photo_id, alternatives=, main_target=, overrides=, rescan=)` regenerates the alternatives of an existing photo without touching the original: it encodes the new files first (a failed run deletes whatever it wrote), swaps `alternatives`/`processing` in the DB, then removes the superseded files and both old and new main-target thumbnails. `overrides` is a dict keyed by processor name; `overrides["Tilt"]` is a `TiltOverride` (`enabled`, manual `angle`, `crop_mode`) whose manual angle becomes a `TiltEstimate(method="manual")` and still applies the tilt step with `Detection method: manual`. The seven corrections use the typed `*Override` classes in `PROCESSOR_OVERRIDES`; `with_overrides()` copies the frozen settings and applies every non-None field, and an `enabled=False` override on a configured processor records a `Not applied / disabled` step so later pipeline passes do not re-enable it. `rescan=True` clears the pixel-derived analysis (`Object`/`PerceptualHash` scanner markers, `objects`, `phash`, duplicate index) and re-queues the photo through the normal pipeline, so the response returns before the scanners finish. One reprocess per photo at a time (`_reprocessing`, HTTP 409); sizes are validated (`MIN/MAX_TARGET_SIZE`, `MAX_TARGETS`), the main size must be generated, and each processor validates its own override (the manual angle is capped at `MAX_MANUAL_ANGLE`) — violations raise `ReprocessError` with 400/404/422.

- **Processors** (`services/processors/`): one class per preprocessing step, modeled on scanners (`Processor` base: `configure`/`accept`/`prepare`/`execute`/`scale`/`ran`, returning `ProcessorResult {image, step}`). Detection, decision and provenance stay inside each `<name>_processor.py`; `processor.py` only holds shared plumbing (`ProcessingContext`, array/alpha helpers, downscaled `analysis_copy`, crop-mode constants). The driver decodes once, lets each processor `prepare` the source (detection, e.g. the horizon estimate or the tone endpoints), pre-downscales by the product of the processors' `scale` hints so the written file still has the target as its longest edge, then runs the chain per target (`execute`) and writes the file. A processor publishes per-photo facts on `ProcessingContext` (the tilt angle/crop mode plus its own `data` entry) for later steps, returns its provenance `step`, and implements `ran(steps)` to say whether the recorded recipe already covers it. `PROCESSOR_DEFINITIONS` fixes the order:
  - `Exposure` (`exposure_processor.py`, config `processing.exposure`): stop-based exposure gain followed by gamma; both are explicit, with no detection. Records the EV/gamma in the `exposure` step. Opt-in.
  - `White balance` (`white_balance_processor.py`, config `processing.white_balance`): Gray World gains measured once on a downscaled sample, or manual temperature/tint gains; `prepare()` stores the decision for every target. Records method, gains and strength in the `white_balance` step. Opt-in.
  - `Contrast` (`contrast_processor.py`, config `processing.contrast`): smooth S-curve or adaptive percentile stretch; `prepare()` measures the black/white points once. Records method, strength and endpoints in the `contrast` step. Opt-in.
  - `Local contrast` (`local_contrast_processor.py`, config `processing.local_contrast`): CLAHE on the LAB lightness channel with a clip limit, tile grid and blend strength. Records its parameters in the `local_contrast` step. Opt-in.
  - `Vibrance` (`vibrance_processor.py`, config `processing.vibrance`): LAB-chroma saturation boost that tapers off for vivid and near-neutral pixels. Records its strength in the `vibrance` step. Opt-in.
  - `Tilt` (`tilt_processor.py`, config `processing.tilt`): owns all horizon logic — pluggable detectors, decision policy, rotation and provenance; records a `tilt` step whenever it is enabled (summary is the angle, or `Not applied` with a reason), with `meta.applied`/`meta.crop_mode`/reference point/line driving the crop and the hover overlay. A per-run override is `TiltOverride` (`enabled`, manual `angle`, `crop_mode`).
  - `Crop` (`crop_processor.py`): trims to `largest_inscribed_rectangle` using the published angle (`crop_mode: maximum_valid_rectangle` by default, `none` keeps the expanded canvas); records a `crop` step only when it trims, and `ran()` treats "no applied tilt" as done.
  - `Noise reduction` (`noise_reduction_processor.py`, config `processing.noise_reduction`): bilateral filter or opt-in, slower non-local means, with its method/parameters in the `noise_reduction` step. Opt-in.
  - `Rescale` (`rescale_processor.py`): resizes each alternative to the target longest edge (never upscales an original smaller than the target) and records the per-target `rescale` step with `Target size`/`Format`/`Quality`.
  - `Sharpening` (`sharpening_processor.py`, config `processing.sharpening`): thresholded unsharp mask after the rescale, so the kernel matches the delivered pixel size; records radius/amount/threshold in the `sharpening` step. Opt-in.

- **Tilt detection** (`processors/tilt_processor.py`, `processing.tilt`): the old `photos/processing` module is gone. Implement `TiltDetector` and call `register_detector`; select with `tilt.method` (default `hough`). The Hough detector downscales the EXIF-transposed original to `analysis_max_dimension` (default 1024 px, so detection never sees the full-size image), runs Canny + `HoughLinesP`, drops short and steep segments, takes the length-weighted median, refines it on the inliers, and scores confidence from the inlier share and the absolute line support. `decide()` applies the conservative policy: below `min_angle` ignored; up to `max_angle` needs `min_confidence`; up to `high_confidence_max_angle` needs `high_confidence`; above it ignored; `auto_apply=false` only records the estimate. The processor owns the rotation and the provenance; `largest_inscribed_rectangle` lives in `crop_processor.py`. `ProcessingService._reconfig_safe = False`, so tilt changes apply on the next start.

- **FolderService** (`photos/folder_service.py`): owns `general.photos_folder`, the trash folder and the originals. `POST /api/photos/upload` writes an original into the photos folder (unique `name_1.ext`, `.part` temp file), and on startup/every 10 s a watcher scans it and pushes every unseen image through `PipelineService.next()`. It never writes processed files; the transient `--failsafe` CLI flag skips the scan and watch for the current run (it is not a config setting). `_requires = ("DatabaseService", "PipelineService")`.

- **Pipelines** (`pipelines/pipeline_service.py`): explicitly registers `CreationPipeline`/`BasicPipeline` (not auto-discovered); `next(item, pipeline=None)` routes to first accepting pipeline — without a `pipeline` arg to the whole list, else after it; when the handing-off pipeline vanished from the list during reconfigure it continues from `pipeline._index` (stored position), so remote photos never re-enter the standard pipeline at index 0
  - External items: `Photo` → `Item` (`photo` + `updated` flag + lazily-cached `image` = main pixels and `original` = original pixels); EXIF reads `item.original`, content scanners read `item.image`
  - `_run_scanners`: runs every scanner's `execute(item)`; last scanner `DatabaseScanner` merges/commits on `item.updated`
  - `CreationPipeline`: `FileScanner`/`ExifScanner`/`ProcessingScanner`/`ThumbnailScanner`/`DatabaseScanner` (`File` and `Processing` are auto-injected into the first local pipeline; `Processing` sits before the first pixel consumer — `Thumbnail`/`Object`/`PerceptualHash` — so analysis sees the alternative)
  - `BasicPipeline`: `ActivityScanner`/`LocationScanner`/`ObjectScanner`/`PerceptualHashScanner`/`RulesScanner`/`DatabaseScanner`; gates routing on `any(scanner.accept(item))`
  - **Defaults**: `DEFAULT_PIPELINES` in `PipelineService`; editor template (`PIPELINES_TEMPLATE`) assembled into API payloads by `add_pipelines_payload` (called from `api/configuration.py`); `ConfigurationService` is purely structural
  - **Cold `_configure`**: materializes defaults into `pipelines` config node when absent/empty; persists to `config.yaml` and round-trips to frontend
  - **Live reconfigure**: `POST /api/configuration` → `_reconfigure_live` (only when `STARTED`); matches pipelines to config by name; unchanged kept (params re-read), changed migrated (old worker stopped, items carried with `take_pending()`, new started), new added, missing removed; response includes `applied` summary via `get_last_reconfigure()`

### Scanners

- **Scanner contract** (`scanners/scanner.py`): non-virtual `configure/accept/execute` → overloadable `configure_/accept_/executePhoto`
  - `configure`: reads `enabled`; `accept`: handles `ForceFlag` (`_forced` toggle), `enabled`, `_forced`, else `accept_`; `execute`: calls `accept` first (declined → `ScannerResult.SUCCESS`), stashes `self._item`, runs `executePhoto` (sync on `ThreadPoolService`), returns `SUCCESS`/`ERROR`, sets `item.updated` if photo changed
  - `DatabaseScanner.accept` = `isinstance(item, Item) and item.updated`

- **Scanner tracking**: `self.add_scanner(photo)` appends name to `photo.scanners` (JSON column, NULL-safe; read via `photo.scanners or []`); `ObjectScanner` runs YOLO on `item.image` (in-memory PIL, no path needed; model `yolo26n.pt`/`yolo26m.pt` in `general.models_folder`), stores `photo.objects` as `{reference: {width, height}, detections: [{label, confidence, box, surface}]}` — `box` is absolute pixels in the detector's decoded image and `reference` is that image's size, so `surface` (0–1, 1/1000) stays valid when a differently sized file is served; gates on `"Object" not in photo.scanners`; image-bearing scanners (`EXIF`/`PerceptualHash`/`Object`) all consume `item.image`, which can be preloaded via `Item(photo, image=...)` for in-memory sources
- **Processing scanner** (`scanners/processing_scanner.py`): the pipeline entry point for preprocessing. `accept_` returns `ProcessingService.needs_processing(photo)`, i.e. it re-queues file-backed photos whose recorded `processing` recipe misses an enabled processor step (remote photos are skipped); `executePhoto` awaits `ProcessingService.preprocess(photo)`, returning whether it ran so `DatabaseScanner` persists the photo. `_can_be_disabled = False`/`_can_be_remote = False`, so it is hidden from the config and Tools scanner lists; `PipelineService` injects it into the first local pipeline and strips it from user config like `File`/`Database`.
- **Heavy flag**: `Scanner._heavy` (default `False`) marks memory-intensive scanners; exposed by `get_scanner_definitions()` and the pipeline scanner chooser. `Object` is the only heavy scanner today, so `HardwareService` can disable it on small machines.
- **No tag scanner**: tags are never inferred from the photo content (not from the YOLO objects, not from the EXIF data) — they are only assigned by the user through the tag API, or by a user-defined **rule** (see Rules)

### Tags

- **Model** (`models/tag.py`): `Tag` table (`tags`) — `id`, `name`, `path` (unique, slash-separated full path), `parent_id`, `depth`, `rules` (JSON list of embedded rule documents); `TagNode` is the API DTO (`count` = photos with exactly this path, `total` = incl. descendants, `rules_count` = rules assigning this exact path, `children`)
- **TagService** (`services/photos/tag_service.py`): owns the registry *shape*; `Photo.tags` (JSON list of full paths) owns the *assignments* — one source of truth per concern, no tag scanner
  - Paths: `normalize()` (trim segments, single `/`), `name_of()`, `parent_path()`, `ancestors()`, `depth_of()`; `MAX_DEPTH = 10` levels
  - `ensure_paths()` registers a path **and its ancestors** (missing parents are created)
  - `seed_defaults()` installs `DEFAULT_TAGS` (32 nodes / 4 roots: Architecture, Animals, Processing, Quality; `Animals/Wildlife` holds the COCO animals and `Processing` the tilt/crop categories); seeded automatically on first start when the `tags` table is empty, so user deletions survive restarts (no config flag)
  - `match()` / `match_exact()`: SQL conditions over `json_each(COALESCE(photo.tags,'[]'))` — `value = :path OR value LIKE :path || '/%'` (exact + descendants), `mode` = `any`/`all`
  - `sync(payload)`: bulk vocabulary write (one request carries the whole tree). Diff = rename (by `id`) → keep → cascade delete → create → describe; a renamed tag moves its descendants **and** the photos carrying them **and** its embedded rules (renamed in place); a deleted parent kills its whole subtree even if the payload still lists a descendant, and its rules go with the rows
  - `delete(tag_id)`: cascade delete of a tag + descendants, stripping them from the photos
  - `set_photo_tags(photo_id, paths)` replaces the whole list of a photo's tags (one call, not incremental)
- **Photo filters**: `GET /api/photos?tags=&tags_mode=any|all&include_descendants=true` and `GET /api/photos/ids` (ids only, used by the gallery/slideshow); `GET /api/photos/custom?tags=` keeps the AND semantics

### Rules

- **Storage**: rules live **on the tag they assign** (`Tag.rules`, a JSON list) — there is no rule table, no FK and no orphan. The owning tag *is* the target: renaming/moving the tag carries its rules, deleting the tag deletes them. Legacy `tag_rule` tables are ignored (never read, never dropped).
- **Rule document**: `{id, name, description, enabled, priority, expression, definition}`. `expression` is kept for display/re-edit; `definition` is authoritative and the backend never parses expression text at evaluation time (only the bundled defaults are parsed once, at install).
- **Definition AST v2** (`services/rules/ast.py`): `{version: 2, match: all|any, conditions}`; a condition is `scalar` (`path`, `op`, `value`), `element` (`key`, `op`, `value`; only inside a collection filter), `collection` (`path`, `quantifier`, `condition`) or recursive `group`. `CollectionCondition.condition` is a full boolean expression in **element scope** (groups, `and`/`or`), so every element condition binds to the **same** element: `objects [label = "dog" and confidence >= 80%] has any`. Quantifiers are `any` (∃), `none` (¬∃), `one` (exactly one) and `all` (∀, vacuously true on an empty list). There is no `detection` condition and no `metric_scale`: stored rules that still hold `detection` conditions fail `RuleRecord.model_validate` and are skipped (no migration; reset the rule rows yourself).
- **Units**: units are optional, generic syntax sugar (`%`, `mm`, `s`, `px`, `B`, prefix `f/`) and are never part of the AST. `%` is the only **semantic** unit: the parser divides the number by 100, so the AST stores the fraction (`80%` → `0.8`) and `confidence`/`surface` ranges are `0..1`. A bare `80` therefore fails range validation; every other unit is ignored (`1200px` → `1200`).
- **Schema** (`services/rules/schema.py`): one descriptor drives validation, evaluation, the generated form and the editor hints — `FieldSpec` (path, group, label, kind, description, value source, static values, computed, min/max/step/unit, `source`) and `CollectionSpec`/`ElementSpec`. `FieldSpec.source` names the path walked over `photo_view` when it differs from `path` (e.g. `processing[step=tilt].meta.applied`). Collections: `objects` (label/confidence/surface), `processing` (step/`meta.applied`/`meta.crop_mode`), `alternatives` (target_size/width/height/file_size/format/main). Scalar fields: EXIF make/model/lens/aperture/ISO/focal length/exposure, image width/height/orientation from `photo.main()` (EXIF fallback), country/location/date/lat/long, `processing.tilt.*`, filename/file size/favorite/tags/scanners, `scores.brisque`. `MAX_CONDITIONS = 20`, `MAX_GROUP_DEPTH = 4`; `validate_definition()` rejects unknown paths/keys/operators/quantifiers, element conditions outside a filter, collections nested in a filter, and values outside the declared range.
- **Metadata view** (`services/rules/metadata.py`): `photo_view(photo)` materializes the photo as a JSON-like dict (derived width/height/orientation/date, `objects` detections, `processing`, `alternatives`); `walk(value, "a.b[step=tilt].c")` follows a dotted path with `[key=value]` selectors — a miss, or a selector with 0 or 2+ hits, returns `MISSING`. `resolve()` walks the field's `source` (or `path`) and coerces numbers from EXIF ratios; `collection_values()` returns the list (empty when missing); `element_value()` walks an element key (dotted keys allowed).
- **RuleService** (`services/rules/rule_service.py`): `_requires = (DatabaseService, TagService, ExpressionEngine)`; embeds CRUD in `Tag.rules`, keeps every rule in `_records` and the enabled ones in `_rules` (refreshed at `_start`, after writes, and from `api/tags.py` after sync/delete) so `RulesScanner` evaluates with no DB round-trip. `schema()` and `values()` serve the editor (bounded dynamic dictionaries, cached for 60 s). `preview()` is read-only and capped at `TEST_SCAN_LIMIT = 5000`; `apply_all()` re-applies enabled rules to the library, add-only.
  - **Bundled rules**: `DEFAULT_RULES` maps a tag path to its expression text (Cat/Dog and the COCO animals under `Animals/Wildlife` with `confidence > 85%` and `surface > 7%`, and the `Processing/Tilt`/`Processing/Crop` recipes). `_start()` calls `install_default_rules()` before `refresh()`: it parses the pending expressions with the editor's own parser (`ExpressionEngineService.temporary()` + `parse(force=True)`, so the engine loads for the install pass even when `javascript_modules` is off, then is released), derives the id from the tag path (`default-animals-pet-cat`), the name from the last segment, and validates the AST. Installed ids are stored in `app_data` (`AppData.DEFAULT_RULES`), so an edited/deleted default is never restored while a default added by a later release installs once; `ensure_paths()` gives existing libraries the new categories. Defaults are enabled with priority 0 and are not auto-applied (use `POST /api/rules/apply`).
- **ExpressionEngineService** (`services/rules/expression_engine_service.py`): loads the standalone frontend bundle (`frontend/dist-expression/expression.js`, built by `npm run build:expression`) in `mini-racer` (V8) and exposes `parse()` / `print()`; the same parser/printer as the editor, with the served schema injected once. The bundle is force-included in the wheel like `frontend/dist`. Gated by `general.javascript_modules` (default `true`, defaulted to `false` by `HardwareService` below 1 GB free; an explicit value wins): when off, the engine is never instantiated and `parse`/`print` raise `ExpressionEngineError`, mapped to HTTP 503 by `api/rules.py`. The flag is re-applied live on `POST /api/configuration` (initial `_configure` runs before the hardware default is known, so it only stores the config node and `_start` applies it). `temporary()` + `parse(..., force=True)` is the one exception: it loads the engine for a startup-only task even when the flag is off and releases it again on exit, so the default rules install without keeping V8 resident on a low-memory machine.
- **Evaluator** (`services/rules/evaluator.py`): AST-only (`matches`, `tags_for_photo`); a scalar condition resolves the field and compares; a collection evaluates its element expression per item and applies the quantifier (`any`/`none`/`one`/`all`). `MISSING` matches nothing; `None` matches only `neq`/`not_contains`; numbers compare through `as_number` and text comparisons are case-insensitive. `confidence`/`surface` are compared as the stored 0–1 values.
- **RulesScanner** (`services/scanners/rules_scanner.py`): a standard scanner registered in `SCANNER_DEFINITIONS` and in `BasicPipeline` **after** `Object` (so detections exist) and **before** `Database` (so tags persist). Gates on `"Rules" not in photo.scanners`, add-only.
- **API** (`api/rules.py`): `GET /api/rules/schema`, `GET /api/rules/values`, `POST /api/rules/expression/parse` (text → AST), `POST /api/rules/expression/print` (AST → canonical text), `GET/POST /api/rules`, `GET/PUT/DELETE /api/rules/{id}`, `POST /api/rules/preview`, `POST /api/rules/apply`.

### Database & Storage

- **DB models**: SQLModel classes in `trailframe/models/` (converter classmethods, e.g. `GarminActivity.to_activity`); tables auto-created at startup, no migrations

- **Generic data** (`core/app_data.py`, model `models/app_data.py`): `app_data` is a key/value table (`key` PK, `value`, `updated_at`) for misc state; `AppData.get_value/set_value` use the running DB session, `read_value(path, key)` reads it synchronously before `DatabaseService` starts (used by `HardwareService._configure`)

- **Thumbnails** (`photos/thumbnail_service.py`): multi-size via `general.thumbnail_sizes` (default `[160, 400]`); files at `{sha1(original path)[:2]}/{sha1}_{main_target}_{size}.webp` (`original` when the main file is the original), so they survive reprocessing at the same target but invalidate when it changes; `generate_all` writes all; `exists` = all present; `delete(photo)` removes every size; `delete_target(photo, target)` removes the sizes of one main target (used when reprocessing swaps it); `select_size` picks lowest ≥ preferred when ≤ 2×preferred else highest below; `GET /api/photos/{id}/thumbnail?size=<p>&v=<n>` (`v` is an ignored cache-busting value)

- **Similarity** (`photos/similarity_service.py`, model `models/similarity.py`): `SimilarityService.candidates()` loads a relative capture-time window around a seed photo and returns `SimilarPhoto` entries (`photo`, `similar`, `score`, `phash_distance`, `shared_objects`) ordered by capture time, never by score. Each photo is scored with perceptual-hash Hamming distance and a Jaccard score over object labels plus coarse `label|aspect|surface` signatures, so detections of the same rough shape match across differently sized images. It is stateless and used only by the multi-edit API.

- **Location boundaries cache** (`map/location_service.py`): `maps/_cache/*.jsonl` — JSON Lines, geometry as base64 WKB; `_read_entries`/`_write_entries` stream line-by-line (never a whole-file parse — the old array format peaked at file+parsed structure, measured 311 MB for `adm0`); unparseable/empty file = cache miss → re-download; superseded `.json` array caches are ignored and deleted on rewrite (no retrocompat); ADM0 download is strictly sequential (convert-to-shapely-and-drop per country, never parallel); `_adm0` resident, `_adm1`/`_adm2` LRU-bounded (`_ADM_CACHE_SIZE`, 16); `_find`/wireframe prefilter use `STRtree`; `_timed_load` logs duration/traced-peak/geometry-size at DEBUG (`LocationService` logger)

- **Favorites**: `Photo.is_favorite` (`_add_missing_columns`); `PUT /api/photos/{id}/favorite`, `GET /api/photos?favorites=true`, `GET /api/photos/favorites`

- **Deletion** (`api/photos.py`): `PhotoService.delete()` discards the alternatives via `ProcessingService.delete_alternatives()`, moves the original to `general.trash_folder` via its provider; `ThumbnailService.delete(photo)` removes the thumbnails; then the DB row is deleted

### API Endpoints

- **Tags** (`api/tags.py`): `GET /api/tags` → the registry tree (`TagNode[]`); `PUT /api/tags` → replace the whole vocabulary in one request (`{"tags": [{id, path}]}`) and return the new tree; `DELETE /api/tags/{id}` → cascade delete of a tag and its descendants
- **Photo files** (`api/photos.py`): `GET /api/photos/{id}/image?size=<target>` serves the matching alternative, or `photo.main()` when omitted/unknown; `GET /api/photos/{id}/preview?size=<px>` serves the **original** pixels for the processing editor — EXIF-transposed, downscaled on the longest edge (default/max `PREVIEW_MAX_SIZE = 2048`), re-encoded to WebP q90 with the exact oriented size in `X-Original-Width`/`X-Original-Height` headers (no EXIF orientation reaches the browser); `POST /api/photos/upload` stores the original through `FolderService` and returns `{filename, path, alternatives}` (empty until the pipeline finishes); `POST /api/photos/{id}/reprocess` (`{alternatives?, main?, tilt?, exposure?, white_balance?, contrast?, local_contrast?, vibrance?, noise_reduction?, sharpening?, rescan?}`) re-encodes from the original and returns the updated `PhotoDetail`. Each correction override carries `enabled` plus its own settings; omitted fields keep the configured values. Tilt uses `{mode: auto|off|manual, angle?, crop_mode?}`. `POST /api/photos/similar-candidates` (`{photo_id, window_seconds, max_hamming, min_object_overlap}`) returns the photos in a relative capture-time window scored by object label/shape signatures and perceptual hash; each entry has `{photo, similar, score, phash_distance, shared_objects}`. `POST /api/photos/reprocess-batch` (`{photo_ids, options}`) applies one `ReprocessRequest`-shaped payload to a selection and returns per-photo results, so one failure does not cancel the rest.
- **Photo tags** (`api/photos.py`): `PUT /api/photos/{id}/tags` → replace the tags of a photo with the given list (`{"tags": [...]}` → `{id, tags}`); `GET /api/photos/ids` → the ids of the photos matching the filters (tags/favorites)

- **Maps/tiles**: `TileService` + `/api/tiles/{z}/{x}/{y}.png` proxy/cache (`general.tiles_folder`, TTL/size under `maps:`)

- **Forced scans** (Tools page): `POST /api/pipeline/scan {"scanners": [...]}`, `GET /api/pipeline/scanners`; `forced_scan(names)`: `ForceFlag(names)` → re-push every `Photo` as `Item`s → `ForceFlag([])`; forced beats `accept_` but honors `enabled`

- **Events** (`api/events.py`): SSE `GET /api/events` streams pipeline status dicts (0.2 s poll, sent on change); `Boundaries` pseudo-category reports `LocationService.get_download_progress()` as `(current/failed/total)` during boundary downloads, then one empty string (frontend drops the category) before the key is omitted; `Text` key → toast via `pushText`

- **Remote scan**: `RemoteScanner` (host side) uploads the photo to `POST /api/pipeline/remote-scan` on the remote server, which runs the delegated scanners on an in-memory `Item(photo, image=...)` (no tmp file) with `photo.source = "Remote"` and returns the enriched fields; force flags propagate via a `forced` form field. `scanners.<Name>.enable_remote` gating lives on the *remote* instance only (`_get_scanner_by_name` on the endpoint), never on the delegating host — the host keeps all scanners configured in the pipeline that are code-capable of remote execution. Host side: `RemoteScanner.accept` intercepts `ForceFlag` (sets `_forced_names` = flag ∩ `_scanner_names`, then forces locally) and folds them into the request. Remote side: `_scanner_cache` reuses cached instances (`_get_scanner_by_name` re-runs `configure`); `_execute_remote_scanners` runs on the shared `ThreadPoolService` and feeds each cached scanner `ForceFlag(forced_names)` before executing then `ForceFlag([])` in `finally`

- **Statistics** (`core/statistics_service.py`): `Scanner._record` times scans; `Pipeline._flush_stats` calls `record_run`, which keeps **one aggregated `ScannerStat` row per scanner** (`count`/`total_ms` accumulate in place, the scanner name is unique, so the table never grows with runs); `GET /api/statistics/scanners` (items/s); `GET /api/statistics/storage` (DB + folder sizes); `FolderStat`/`StorageStats` are pydantic shapes in `api/statistics.py`, not DB tables; for tests: insert mock `ScannerStat` rows, don't run real scans

- **Docs/version** (`api/docs.py`, `api/about.py`): `GET /api/docs` lists bundled Markdown documents (`hardware`, `tutorial`, `whats-new`), `GET /api/docs/{name}` returns `{name, title, description, content}` from `trailframe/docs/*.md` (whitelisted names, `importlib.resources` so the wheel works); `GET /api/about/version` returns `trailframe.version.app_version()` (installed metadata → generated `_version.py` → `0.0.0`), also used as the FastAPI version

### Rules UI

- **`src/lib/rules.ts`**: the AST model matching the backend (`Definition`, `ScalarCondition`, `ElementCondition`, `CollectionCondition`, `GroupCondition`, `Quantifier`) plus the draft (`RuleDraft`) and conversions (`emptyRule`, `toDraft`, `toPayload`); `countConditions` recurses into groups and collection filters.
- **`src/lib/expression/`**: the **fully local** language — `tokens.ts` (tokenizer, UTF-16 spans, including `%` and the `f/` prefix unit), `parser.ts` (**schema-free**: `and`/`or`/`not`/parentheses, `path op value[unit]`, `path is [not] true|false`, `path in [..]`, and `collection [predicate] has any|none|one|all`; the predicate is a full boolean expression over element keys, so `objects [(label = "dog" or label = "cat") and confidence >= 50%] has any` binds each constraint to one element; a bare key without a comparison is rejected; `not` is lowered by operator negation / De Morgan, and `not` before a collection is a parse error suggesting `has none`), `printer.ts` (AST → canonical text, re-emitting units from the schema and multiplying `%` back to 0–100), `schema.ts` (validation against the served descriptor, including the 0–1 percent ranges), `units.ts` (known units, prefix detection), `context.ts` (shared caret context; `currentSegment` tracks bracket depth so `and`/`or` inside a filter do not split the outer condition), `hints.ts` (contextual hints: fields and collections at a condition start, then the field's operators, then its values; inside a filter the element keys, their operators and values, then `and`/`or`/`] has …`; after the filter the quantifiers; a step keyword that is already typed — `field is`/`is not`/`contains`/`in`, `] has`, a trailing `and`/`or` — advances to the next step even without a trailing space), `typing.ts` (typing aids: an operator picked from the hints arms unit filling for the number typed next, and only while the expression still has a parse error, so units never stack; space/comma steps over the unit, a closing quote is skipped, the first letter of a text value is quoted). It never calls the backend per keystroke. Vitest covers parse/print/validate/hints/typing (`npm test`).
- **`src/components/ExpressionEditor.tsx`**: transparent textarea over a syntax-coloured overlay (keywords, fields, strings, numbers, dates, units, operators); reports parse issues and pauses previews during IME composition. Under a focused editor it shows the contextual hint chips (`schema` + `values` props); clicking a chip or pressing Tab inserts the first hint at the caret, honouring the hint's caret offset. Printable typing goes through `typing.ts` (units, quotes).
- **`src/components/SchemaForm.tsx`**: the generated form — field/operator selects, value editors by kind, collection rows (path + quantifier + element conditions), add/remove; labels, operators, bounds/step and suggestions all come from `GET /api/rules/schema` + `GET /api/rules/values` (fetched once when the editor opens). Percent inputs show and edit the 0–100 scale while the AST stores the fraction; new numbers start at the middle of the served range. Nested groups are round-tripped from the text; the form edits flat top-level conditions first.
- **`src/hooks/useRulePreview.ts`**: debounced (450 ms) preview with a **local-validity gate**, one request in flight, latest-wins coalescing, identical-definition suppression, and `POST /api/rules/preview`.
- **`src/components/RulePage.tsx`**: the editor — expression on top, generated schema form below, header (name/description/priority/enabled/revert/save) and the expected-matches panel; Save sends `POST /api/rules` or `PUT /api/rules/{id}`. The expression is always reprinted from the stored `definition` (percent, not the legacy fraction text) and again with units once the schema arrives; the expression text is then authoritative in the browser, and only a locally valid AST is ever sent.
- **`src/pages/TagsPage.tsx`**: opens `RulePage` from a tag's inner page; it no longer has a separate Rules tab.
